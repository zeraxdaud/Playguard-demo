# Проверка основных сценариев

## Автоматически

Запустить:

```bash
npm test
npm run build
```

Ожидается: все тесты зелёные, папка `dist` создана.

## Вручную на настроенном Supabase

Используйте только вымышленные данные и два отдельных email, к которым у вас есть доступ.

### 1. Регистрация и компания

- Зарегистрировать пользователя A с названием «Тестовая компания A».
- Убедиться, что открывается пустой dashboard.
- В «Команда» роль пользователя A должна быть `OWNER`.

### 2. Общая база

- A добавляет клиента и договор.
- Создано ровно указанное число платежей; их сумма равна сумме договора минус взнос.
- A приглашает пользователя B как `MANAGER`.
- B открывает ссылку, регистрируется с приглашённым email и видит того же клиента и договор.
- B добавляет клиента; после обновления A видит запись.

### 3. Роли

- A меняет B на `VIEWER`.
- У B исчезают кнопки добавления и оплаты.
- Прямой `insert` от сессии B должен вернуть ошибку RLS.
- A меняет B на `ADMIN`; B может пригласить `MANAGER`, но не может назначить `OWNER`.
- Попытка удалить или понизить последнего `OWNER` должна завершиться ошибкой.

### 4. Изоляция tenants

- Создать отдельную компанию C у пользователя C.
- Пользователь B не должен получить клиентов C ни списком, ни запросом по известному UUID.
- При подмене `company_id` при создании клиента запрос должен быть отклонён RLS.
- Договор нельзя создать с клиентом из другой компании: RPC должна вернуть ошибку.

### 5. Платежи

- Записать частичную оплату: статус графика становится `PARTIAL`.
- Записать остаток: статус становится `PAID`.
- Сумма больше остатка должна быть отклонена.
- После оплаты всех частей договор получает `COMPLETED`.
- Неоплаченная дата в прошлом получает `OVERDUE` при загрузке workspace.

### 6. Приглашения

- Ссылка принимается только email, указанным владельцем.
- Повторное использование ссылки отклоняется.
- Истёкшая ссылка отклоняется.
- В базе хранится SHA-256 hash, а не исходный токен.

### 7. Mobile-first

- Проверить ширины 320, 375, 390 и 430 px.
- Нижняя навигация не перекрывает контент и учитывает safe area iPhone.
- Формы открываются снизу, все цели нажатия не меньше 38–44 px.
- На ширине от 760 px навигация перемещается в левую колонку.

### 8. Risk Score

- `MANAGER` создаёт проверку, и она появляется у `OWNER` через Realtime.
- Сильный первоначальный взнос и низкая нагрузка дают низкий риск.
- Нагрузка выше 70% и просрочка 90+ дней дают высокий риск.
- `VIEWER` видит историю, но не может выполнить проверку.
- Попытка записать проверку для другой компании отклоняется серверной функцией.
